# feature/source — источник задач с противодавлением

Часть проекта [Resume Classifier](../../tree/main). Влита в `main` через [PR #28](../../pull/28).
Вторая из трёх веток ДЗ 4.

## Что сделано

- **`source.py`** — пакетный скоринг файла: читает CSV построчно и каждую строку публикует как
  задачу в очередь `tasks`.
- Сервис `source` в `docker-compose.yml` с профилем `load`: обычный `docker compose up` его не
  запускает.
- Раз в 5 секунд источник пишет в лог, сколько задач принято и сколько раз брокер отказал.
- 3 новых теста, один из них интеграционный на настоящем RabbitMQ.

## Как источник замедляется

1. Очередь `tasks` ограничена (`x-max-length: 100`, `x-overflow: reject-publish`), публикация идёт
   с подтверждениями (publisher confirms включены в FastStream по умолчанию).
2. Пока в очереди есть место, брокер подтверждает публикацию (`basic.ack`), и источник сразу берёт
   следующую строку.
3. Когда очередь полна, брокер отвечает `basic.nack`, и `publish` бросает `DeliveryError`.
   Источник ждёт и повторяет ту же задачу: 0,05 → 0,1 → 0,2 → … → 2 с, после успеха пауза снова
   начинается с 0,05 с.
4. Следующая строка файла читается только после того, как предыдущая принята. Задачи не теряются и
   не копятся в памяти: в работе у источника всегда ровно одна задача.

В установившемся режиме очередь стоит у лимита, и источник публикует ровно столько, сколько
воркеры успевают разобрать: 8 задач/с с одним воркером, 16 — с двумя. Лимит частоты нигде не
задан, скорость подстраивается сама — это видно в эксперименте ветки
[`feature/experiment`](../../tree/feature/experiment).

## Почему такой механизм

Сигнал о перегрузке приходит от самого брокера в ответ на каждую публикацию — точно, без задержки и
без отдельных запросов. Рассмотренные альтернативы:

| Вариант | Почему отказались |
|---|---|
| Опрашивать глубину очереди через Management API | статистика обновляется раз в 5 с; между проверкой и публикацией очередь успевает измениться; источнику нужны отдельный доступ и HTTP-клиент; нагрузка на плагин управления |
| Публиковать с фиксированной частотой | это rate limiting: частоту надо подбирать вручную, она не растёт при добавлении воркера и не падает при замедлении |
| Встроенный flow control RabbitMQ (memory alarm) | срабатывает только при нехватке памяти у всего брокера и блокирует все соединения, включая API |
| `x-overflow: drop-head` | при переполнении брокер выбрасывает старые задачи — потеря данных |
| `reject-publish-dlx` | не поддерживается quorum-очередями и уводит задачи в DLQ вместо того, чтобы замедлить источник |
| Очередь без лимита | задачи копятся в брокере, растут память и время ожидания — видно в эксперименте |
| Повтор публикации без паузы | busy loop: источник нагружает брокер отказами |

## Как проверить

Источник читает подготовленные тексты резюме из `data/evaluation/full.csv` (как его собрать — в
[`data/README.md`](data/README.md)):

```bash
docker compose --profile load up -d source
docker compose logs -f source
```

В веб-интерфейсе RabbitMQ (http://127.0.0.1:15672, очередь `tasks`) видно, что глубина очереди
доходит до лимита и дальше не растёт.
